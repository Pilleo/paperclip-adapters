# Architecture & Lifecycle Engine

The Jules adapter acts as a stateful, resilient bridge between Paperclip's bounded execution model and Google's asynchronous Jules API.

---

## 🏛️ Core Architectural Invariants

### 1. Pure State Machine & The Intent Pattern (`state-engine.ts`)
State transitions are evaluated via pure functions (`evaluateJulesLifecycleState`) that accept external signals (`julesState`, `prDetails`, `unreadReviewComments`, `ciStatus`) and return a deterministic `JulesLifecyclePlan`. No inline network side-effects occur inside conditional branches.

```
(SessionState, ExternalSignals) ──► [ Pure Evaluator: state-engine.ts ] ──► TransitionPlan ──► [ Atomic Executor ]
```

### 2. Typed Disposition Invariants (`disposition.ts`)
Paperclip server disposition prerequisites are modeled as compile-time types (`InReviewDisposition`, `InProgressDisposition`, `BlockedDisposition`, `DoneDisposition`).
- Moving an issue to `in_review` requires a linked interaction card or an assigned reviewer.
- Unbacked agent-authored status mutations that would trigger HTTP 422 `invalid_issue_disposition` are prevented before issuing network requests.

### 3. Review Feedback Loop (`PR_REVIEW_LOOP`)
When Jules creates a Pull Request:
- The Jules cloud session remains **active** in the session store (`shouldDeleteSession: false`).
- Review feedback generated by the Paperclip Code Reviewer is delivered **directly to the Jules Cloud Session API** via `client.sendMessage(sessionId, ...)`.
- Review feedback is not posted as PR comments on GitHub to avoid noise.
- Sessions are only purged when the GitHub PR is merged or the operator confirms task completion.

### 4. Direct Session Heartbeat & Watchdog (`watchdog.ts`)
- Each Paperclip heartbeat polls Jules once, persists `sessionParams` / `sessionDisplayId`, and yields with `retryNotBefore` from `pollCadenceSeconds`. The host process must not sit in a multi-hour poll loop.
- `sessionDeadlineMinutes` (default 2880 = 48h) is the Jules **cloud session** TTL. A live remote session is still polled after that mark; the adapter must not create a replacement Jules session.
- The watchdog checks session idle times every 15 minutes across those yielded heartbeats.
- Keepalive nudges (`client.sendMessage`) are sent periodically if Jules remains silent without progress.

---

## 🔄 Core Flow

1. **Initialization:** Validates credentials and generates a deterministic prompt combining instructions, issue context, target symbols, and branch details.
2. **Session Creation:** Creates a new asynchronous Jules session in Google Cloud.
3. **Heartbeat Polling Loop:** One poll per Paperclip heartbeat, then yield so a days-long Jules session can survive host restarts.
4. **Interactive Decisions:**
   - `AWAITING_PLAN_APPROVAL`: Evaluated by Terra. Clear plans are auto-approved via `client.approvePlan`; plans with architectural questions escalate to the operator via Paperclip approval cards.
   - `AWAITING_USER_FEEDBACK`: Answered inquiries are pushed to Jules via `client.sendMessage`.
   - `COMPLETED`: Pull request work product is registered in Paperclip, and the session enters the review loop.
5. **Code Review & Re-Review Loop:**
   - The Orchestrator routes the task to the Code Reviewer once CI is 100% green.
   - `REQUEST_CHANGES` verdicts reassign the issue back to the Jules worker and forward review feedback directly into the Jules session context.
   - Jules applies fixes and pushes commits to the PR branch.
6. **Completion & Cleanup:** When the PR is merged on GitHub, the state engine transitions the issue to `done` and clears the stored session.
