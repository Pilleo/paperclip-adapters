# Paperclip API stalls during fleet reconciliation

The local Paperclip `2026.916.0` server is unmodified. The host runs embedded PostgreSQL and the orchestrator external adapter from this repository. This is observation evidence, not a claim that the database or a particular query is the root cause.

## Reproducible observations

- Before the orchestrator correction, service logs contained 59 `Managed Jules agent` ticks and 59 successful `Applied Jules plan policy: undefined` messages in ten minutes. The policy comparison treated an unset project override as a mismatch with the worker's stored `required` policy; it also compared the question reviewer to Terra when the actual PATCH gives precedence to the Terra adjudicator.
- A test-first change compares only explicitly managed, visible fields and uses the effective question reviewer. The full orchestrator suite (111 test files) and package build passed. After rebuilding and reloading `dist/index.js`, the first seven observed managed-Jules ticks recorded **zero** plan-policy PATCHes. The service's previously running heartbeat failed after the restart; a queued heartbeat started automatically. No manual run retry was made.
- During that new heartbeat, six of eight unauthenticated `GET /api/health` probes timed out at five seconds. TCP connection time stayed near 0.2 ms; no response bytes arrived before timeout. Eliminating the redundant PATCH did **not** eliminate the stalls.
- A later health request took 2.06 seconds while all ten observed embedded PostgreSQL client backends were busy: eight showed `SELECT`, one `BIND`, and one `PARSE` in process titles. This is consistent with database connection contention, but process titles cannot identify which SQL or caller held those connections.
- The installed, unpatched host health handler (`@paperclipai/server/dist/routes/health.js`) awaits `SELECT 1`, an instance-admin role count for authenticated deployments, and a native recovery summary for callers allowed full details. A slow `/api/health` response therefore cannot alone establish that the Node event loop was blocked: the handler also depends on database access.
- A separate read-only connection to the embedded database confirmed the contention in the same window. Across 48 bounded health probes, 18 exceeded 500 ms or timed out; several timed out at 4.5 seconds while ten Paperclip PostgreSQL backends were active. A recurring active query fingerprint (`6e1f5e4ac48b`, truncated SHA-256 of the observed query text) selects a full `heartbeat_runs` row. PostgreSQL's default activity-query text limit truncates this 1,023-character projection **before the FROM/WHERE clause**, so the fingerprint cannot distinguish the caller or filter. Backend snapshots showed ten concurrent executions of that query prefix; other snapshots showed reads of issues and related recovery tables. `heartbeat_runs` has approximately 81,683 rows and occupies about 801 MB including indexes. No SQL text containing literals or connection credentials was written to this evidence file.

## Additional native query attribution (not the identified adapter load source)

The full-row `heartbeat_runs` SELECT still has an unattributed caller and predicate: read-only `pg_stat_activity` reports null `query_id` on this host and cuts off before the predicate. Investigate it separately using bounded tracing or a contract environment if API stalls recur; the issue-detail request fan-out identified below is independently demonstrated by a failing adapter regression. Do not change production PostgreSQL settings or installed Paperclip code to inspect this query. Preserve the current Jules execution/recovery holds.

## Additional baseline during plan execution

- The current checkout is `master` with extensive existing uncommitted work. The previously interrupted orchestrator run `5a28e4a7-8f8c-403f-95ca-8d162ded45c3` has native error code `process_lost`; later orchestrator runs `22566323-df88-40bb-8af9-b465fbfa99ad` and `146b1dfb-9c4e-4c52-8d07-007ac5e35dae` succeeded. That does **not** prove the Jules/reviewer/PR chain.
- The same bounded project-issues request returned HTTP 200 in 0.227 seconds at one instant, then separate company-run and issue-ID GETs timed out at eight and ten seconds during another interval. MAZ-1578 remained `blocked` in a separate read-only SQL query that completed in under 0.3 seconds. The source of the API delay is not established by those timings.
- One synchronized five-second health timeout coincided with all ten Paperclip PostgreSQL connections running the **same short issues SELECT** (`dfca373b4606`, query-text SHA-256 prefix): its projection reads `conversation_agent_id` and `conversation_boundary_comment_id`. A different slow interval had ten active full-row `heartbeat_runs` SELECTs. The issue projection also occurs in installed Paperclip's issue-list and heartbeat-related services, but the captured hash alone does not establish which caller issued it. The bottleneck is **not limited to one heartbeat-run query shape**.
- During another health request, Paperclip used approximately seven CPU seconds over 5.7 wall seconds and its database backends were not all busy (three to seven observed active); the response arrived after 5.5 seconds. Database saturation alone is therefore not a sufficient explanation for every timeout. No adapter source or live database configuration was changed during these observations.

## Bounded issue-hydration correction (later on 2026-09-27)

An adapter-owned source of load is now identified: `packages/orchestrator/src/server/execute.ts` previously used `Promise.all(scopedIssues.map(...pc.getIssue))` for every terminal/review/blocked issue. Read-only counts show 518 qualifying statuses in a 918-issue project and 388 in a 543-issue project. The live host logged as many as 2,546 successful issue-detail GETs in one minute during the failing interval; the API separately timed out on a single issue read. This establishes an unbounded adapter request fan-out, but it does not establish that *every* host API stall had that sole cause.

The regression `orchestrator native PR completion > bounds issue detail requests when a project has many terminal issues` failed with **18 simultaneous requests** before the change. Hydration is now capped at four concurrent detail GETs, preserving issue order and the established selection policy. A second regression failed before the follow-up fix and now requires the tick to fail closed if any required detail GET fails; the adapter no longer silently proceeds with an incomplete PR/recovery view. Both regressions passed; all 111 orchestrator test files, the affected package build, and the authenticated `pnpm test:contract:child-plan-review --require-safe` contract passed on unpatched Paperclip `2026.916.0` with disposable PostgreSQL.

The live service was reloaded only after a read-only query confirmed no queued/running orchestrator, Jules, Luna, or Gemini run. Startup loaded orchestrator `./dist/index.js` at 19:16:46 local time. Twelve subsequent health requests and twelve project-scoped issue-list requests across actual project ticks all returned HTTP 200: health ranged approximately 0.004–0.135 seconds and issues approximately 0.019–0.131 seconds. No `Failed to fetch issues` or `Failed to fetch issue detail` was observed in that window. New orchestrator run `88e6dfa5-fdca-4e9b-862f-26c8766d32e3` succeeded; a second complete post-reload run and the Jules provider gate remain pending at this checkpoint.

The next native orchestrator run `baf2617f-...` also succeeded. Three additional health/project-issues probe pairs during that second run all returned HTTP 200; health took 0.019–0.032 seconds and issues 0.027–0.302 seconds. A read-only run-status query found **two succeeded and zero failed** orchestrator runs since the reload, no Jules/Luna/Gemini runs, and MAZ-1578 still `blocked` with the same Jules assignee and `updated_at`. These observations pass the bounded two-cycle host gate; they do **not** qualify the independent Jules provider gate or prove that all possible host load has been eliminated.
