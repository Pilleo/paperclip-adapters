## Interpretation and stop decision

The direct control rules out Paperclip's monitor scheduling as the *sole* cause: it reproduced without Paperclip execution. The REST API describes `requirePlanApproval: true` as requiring explicit approval before work begins, but [Jules's planning guide](https://jules.google/docs/review-plan/) says it eventually **auto-approves plans on a timer** when the user navigates away. The observed transition is consistent with that documented UI timer; the API exposes neither a timer override nor an attributable `planApproved` event in these session histories. The absence of the input-only flag in GET is not evidence it was omitted at create time.

Stop condition: retain the native recovery hold on MAZ-1578. Do not approve the terminal session, synthesize a verdict, replace its provider session automatically, or create another canary to hide the result. Further live work requires a supported provider-side guarantee or a verified continuation contract preserving exact session and plan identity.
